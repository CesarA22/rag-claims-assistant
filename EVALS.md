**What that costs, stated plainly.** Answer *quality* is not measured in this file. Cost per question, the cached-versus-uncached split, and latency are not measured either — `FakeProvider` bills nothing and returns in microseconds, so the numbers in that section describe the harness, not the system. The four judge cases are ungraded, because the judge needs the same credits.

**What is measured, and why it is real.** The three outcomes the brief grades — refusal, clarification and PII — are decided in `app/services/grounding.py` by deterministic code that runs *after* the model and overrules it. So the hard gates below, the refusal and ambiguity behaviour, retrieval, and the boundary suite are genuine measurements of the shipped system against the real 220-chunk corpus. They would not move if the provider were swapped. That distinction is the reason this file is worth reading at all, and it is also the reason the content assertions (`must_contain`, `must_cite`) below are *not* evidence of anything: a fake that knows one sentence cannot answer gs-004.

**To produce the live tier:** add credits, then
`LLM_PROVIDER=openai RETRIEVER_ARM=hybrid` on the API and `python -m evals.run_golden --base-url http://127.0.0.1:8000 --runs 3`, then `python -m evals.judge_run` and regenerate. The thresholds do not move; they are already committed.

**Runs:** 3, executed consecutively so the provider prompt cache is a named variance driver rather than an artefact of spacing.

## Findings

### 1. The sufficiency gate is unreachable for gs-008, because ambiguity is checked first

The headline result, and it is provider-independent.

`judge()` in `app/services/ask.py` runs its gates in this order: PII, then the
model's own refusal, then **ambiguity**, then citation validation, then
**sufficiency**. gs-008 asks about a premium discount that does not exist in the
corpus. Retrieval returns five confident payment chunks spanning three products:

```
gs-008 evidence products : ['Auto', 'Auto', 'Empresarial', 'Residencial', 'All']
spanned                  : {Auto, Residencial, Empresarial}   names_product: False
is_ambiguous             : True
model attempts an answer -> judge: needs_clarification
model refuses itself     -> judge: refused
```

So gs-008 returns `needs_clarification`, and `must_be_refusal` fails. The
sufficiency gate — R-02's deterministic backstop, the one T-16 was written for,
the one whose whole purpose is that we do not have to trust the model to refuse
— **never executes for this question**. Whether gs-008 passes depends entirely on
whether the model volunteers a refusal on its own.

That is the opposite of the architectural claim the project makes. It is not a
fake-provider artefact: `is_ambiguous` is deterministic code that overrules
whatever the draft said, and it fires here for any provider.

The fix is a reordering — sufficiency before ambiguity, or ambiguity only when
the draft is otherwise answerable and supported — plus a test that pins the
order. **It is not applied here**, because the plan says a boundary finding gets
its own commit with its own test rather than a quiet patch inside the session
that reports it.

### 2. gs-007 fails because the claims tool is not wired into the pipeline

Registered in `thresholds.yaml` before the run, not excused after it.
`app/services/ask.py` contains no reference to `app.tools`; the only importers in
the repository are `tests/test_claims.py` and `scripts/gs007_from_db.py` — the
standalone script S4 wrote to answer gs-007 from the database *by hand*, which is
itself the evidence that the pipeline cannot. `must_cite
'claims.get_claim_payment'` can never be satisfied.

`LLMProvider.complete` has no `tools` parameter, so wiring it changes the
Protocol, all three providers and `ask.py`, and needs its own tests. R-10 drops
from `done` to `partial` in the register as a result: the queries are real and
T-20…T-26 pass, but a capability the product cannot reach is not done.

### 3. gs-009 carries assertions the shipped behaviour would fail, and they are not asserted

Said out loud rather than left for a reader to notice. gs-009 is a `judge` case
carrying `must_contain: ['5.000', '3.000']` and `must_cite: ['CG-AUTO-2024',
'CG-RES-2024']`. The system returns `needs_clarification` with **zero
citations**, naming neither figure — so it would fail both if they were applied.

They are not applied, because deterministic assertions run on deterministic cases
and gs-009 is graded by judge. Its own `criterio_de_acerto` says the correct
answer *"explicita essa premissa **ou** pergunta de qual produto se trata"* —
asking is a pass by the case's own stated criterion, and the trap it was written
for (`"a single unqualified number FAILS"`) is avoided. Burying this would have
been the only dishonest thing in the file.

### 4. One instrument was corrected before the run, and the threshold did not move

The error-leakage gate originally scanned every response for `"gpt-5"`. A
successful envelope carries `meta.model` on purpose — it is provenance, and T-02
asserts it — so that check would have failed all thirty live responses for doing
exactly what they were built to do. `00-architecture.mdc` scopes the prohibition
to **errors**: *"errors returned to the client never contain the model name, the
prompt, or a traceback."*

It now allows the model name in `meta.model` and nowhere else: `meta.model` is
lifted out and the rest of the body is still scanned for it, so a model name
reaching `answer` or a citation snippet is still a leak. That is stricter than
what it replaced, not looser, and the threshold (`error_leakage: 0`) is
unchanged.

Recorded because the timing matters: it was caught by evaluating the check
against a synthetic 200 envelope **before** any live result existed, and the
keyless proof run could not have caught it — `FakeProvider` reports model
`fake-1`. Commit `1cbf48f`, before the runs.

## Refusal precision and recall

A refusal is `outcome == "refused"`. `needs_clarification` is a third outcome, counted as neither a refusal nor a false one — so gs-009 is scored as neither, and neither is gs-008, which is the finding above.

**Golden set, as a count (n=2):** 1 of 2 cases that must refuse did refuse (gs-010). 6 cases refused that should not have (gs-002, gs-003, gs-004, gs-005, gs-006, gs-007).

A percentage off two samples would be the least honest number in this file, so it is not given. The false refusals are all `FakeProvider` artefacts — the sufficiency gate correctly rejects a canned sentence that the evidence does not support — and they are exactly the measurement that needs the live model to mean anything. Precision over the combined golden + boundary population is therefore also withheld rather than computed from a population the provider poisoned.

## Reproducing this

```bash
docker compose up -d db
alembic upgrade head
python -m app.retrieval.ingest data/corpus --no-embed     # keyless; lexical arm

STORAGE=sql RETRIEVER=hybrid RETRIEVER_ARM=lexical LLM_PROVIDER=fake \
  uvicorn app.main:app --port 8000 &

python -m evals.run_golden --base-url http://127.0.0.1:8000 --runs 3
python -m evals.boundary  --base-url http://127.0.0.1:8000
python evals/retrieval_baseline.py --k 5 --arm lexical > evals/results/tier0.txt
python -m evals.report --results evals/results --out EVALS.md
```

Raw envelopes, token counts, latencies and every assertion result are committed
under `evals/results/`, so any number above can be recomputed rather than taken
on trust. That is also the only way this file survives the charge that it was
written on day five to match the gates.
