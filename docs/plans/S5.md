# S5 — the resilient decorator, the error surface, and chaos

**Goal.** The LLM stops being a function call and becomes what the brief says it
is: an expensive, slow, unreliable external dependency. `app/llm/resilient.py`
holds every policy that fact implies — a request budget that derives each call's
timeout from what is left, selective bounded retry with jittered backoff, a
circuit breaker whose thresholds are configuration, and the classification of
which rung of the degradation ladder a failure lands on. `app/api/errors.py`
turns typed failures into RFC 9457 `problem+json` with a `trace_id` while the
model name and the prompt go to a structured log and nowhere else.
`app/llm/chaos.py` makes all of it visible without an API key.

**Why this shape.** This is the heaviest-weighted part of the evaluation and the
one most easily faked. A retry loop inside `ask.py` would satisfy a reading of
the requirement and fail the point of it: the pipeline would then know about
timeouts, and swapping the provider would mean re-reading the pipeline. The
decorator is the seam that makes `ask.py` oblivious, and the only way to prove
it is oblivious is that `ask.py` never passes `timeout_s` and never counts an
attempt.

## Decisions taken before writing this

### 1. The decorator classifies the failure; `ask.py` decides what it can still show

The excerpts live in the pipeline, not in the decorator. That is a rendering
concern, not a policy one. So:

- `ResilientProvider.complete()` raises **`ProviderDegraded`** when it has
  exhausted its attempts on a *retryable* failure, and **`CircuitOpen`** when
  the breaker refused the call. Both mean "no model output is coming."
- A non-retryable failure (`InvalidRequest`) propagates unchanged and is a 400.
- `ask.py` gains exactly one new branch:
  `except (ProviderDegraded, CircuitOpen) as exc:` → if evidence is non-empty,
  emit the excerpt answer with `meta.reason = exc.code`; otherwise re-raise.

**The branch keys on evidence, not on which failure got us here.** From the
analyst's seat those two failures are one experience: the assistant cannot
summarise, here are the sources. See 6.

The load-bearing consequence: a raw provider error that reaches `ask.py` without
passing through the decorator still becomes a 503. That keeps T-10 honest —
`ask.py` does not degrade on "any provider exception", it degrades on the
decorator's explicit signal.

### 2. The per-question budget is ambient, not a parameter

`LLMProvider.complete(messages, *, schema, timeout_s)` is frozen by the seam and
S1 already ruled out speculative parameters. But the decorator must consult a
ledger that spans the whole question (two model calls share one US$0.05 and one
6 s wall), and the decorator is a long-lived singleton on `app.state`.

`app/services/budget.py` therefore holds a `QuestionBudget` — deadline plus cost
ledger — published on a `ContextVar` that `ask.py` enters once per turn:

```python
with question_budget() as budget:      # sets the ContextVar
    ...
    completion = await llm.complete(messages, schema=DRAFT_SCHEMA)
```

The decorator reads `current_budget()`. If none is set (a unit test calling the
decorator directly), it creates a private one for that call.

This is the one piece of implicit coupling in an otherwise explicit codebase, so
the justification is written down rather than assumed: **the alternative threads
a budget parameter through the `LLMProvider` Protocol, which pushes a
cross-cutting concern into every implementation — including the fake and the
chaos provider, neither of which spends anything.** A cost ledger is ambient by
nature; making it a parameter taxes four implementations to serve one.

Two implementation constraints that follow from `ContextVar` semantics and are
easy to get wrong:

- **The ledger is mutated in place, never rebound.** A child task inherits a
  *copy* of the context, so `ContextVar.set()` inside a task never reaches the
  parent. Spend from parallel tool calls only accumulates if every writer calls
  `budget.charge(...)` on the shared object. `question_budget()` sets the var
  once, at the top of the turn, and nothing else ever sets it.
- The deadline lives on the same object, so two model calls in one question
  share one 6 s wall as well as one US$0.05.

`budget.py` owns facts (what was spent, what remains). `resilient.py` owns
judgment (whether that is enough to try again). The cost ledger also finally
makes `meta.cost_usd` real — it has been hardcoded `0.0` since S1.

### 3. Timeouts are derived, twice, and the second one is not trust

Per attempt: `remaining = deadline - now()`. If `remaining < min_retry_budget_s`,
do not start the call — degrade. Otherwise pass `timeout_s=remaining` down
**and** wrap the await in `asyncio.wait_for(..., remaining)`. The parameter is
a courtesy to a provider that honours it; the `wait_for` is the guarantee for
one that does not. `asyncio.TimeoutError` maps to `ProviderTimeout` at that
boundary so everything above sees one vocabulary.

**The threshold is minimum-*viable*-remaining, not `remaining > 0`.** A typical
call is ~2 s. Starting one with 0.4 s left spends the rest of the latency budget
to arrive at exactly the degraded answer we would have produced immediately —
the analyst waits the full 8 s for the same excerpts. `LLM_MIN_RETRY_BUDGET_S`
(default 1.5 s) is the one knob, applied both before the first attempt and after
backoff, because two near-identical numbers would only invite one of them to
drift.

### 4. Retry classification is a frozen set, not a predicate on strings

Retryable: `ProviderTimeout`, `ProviderUnavailable`, `RateLimited`
(429 / 5xx / timeout / connection). Never retryable: `InvalidRequest`, schema
validation failure, anything unrecognised. Backoff is full jitter —
`random() * min(base * 2**attempt, cap)` — because synchronised retry is how a
provider blip becomes a provider outage.

Before each retry, **both** gates:

- Time: `remaining_s() > backoff_delay + min_retry_budget_s`, else degrade.
- Cost: `spent + estimate(next call) <= ceiling`, else degrade.

The cost estimate cannot come from the failed attempt — a timeout returns no
usage. It comes from `budget.estimate(messages, model)`, a character-count
heuristic priced at the input tier.

**It divides by 3, not by 4, and the bias is the point.** The conventional
4-chars-per-token rule is a central estimate, and a central estimate on a
*ceiling* gate is wrong half the time in the only direction that matters: an
under-estimate waves through the retry that breaches US$0.05, which is the one
outcome the gate exists to prevent. Dividing by 3 rounds against us — we
occasionally degrade a question we could have afforded, and never bill one we
could not. That trade goes in `DECISIONS.md` in those words.

### 5. Breaker thresholds are configuration, and half-open is single-flight

Closed → open after N *consecutive retryable* failures → after `reset_s`, one
half-open probe → success closes and resets, failure re-opens with a fresh
timestamp. `InvalidRequest` never trips it: a malformed request is our fault,
and letting it open the breaker would take the app down over a bug in one
question. State lives on the decorator instance (one per process, hung on
`app.state`), and every transition is a structured log line.

**Exactly one probe.** A half-open state that lets every waiting request through
is the stampede the breaker was built to stop — twenty analysts hit Retry at
`reset_s + 1` and a recovering provider gets twenty concurrent calls. The probe
is claimed with a non-blocking `asyncio.Lock` (or an atomic flag; the loop is
single-threaded, so `if not self._probing: self._probing = True` across no
`await` is sufficient and cheaper). The claimant calls; everyone else gets
`CircuitOpen` immediately and renders excerpts. This is asserted under real
concurrency, because it is the failure mode that only appears there.

### 6. Every rung with evidence in hand serves excerpts — including an open breaker

The original ladder in `00-architecture.mdc` splits rung 2 ("provider down,
retrieval up → excerpts") from rung 3 ("circuit open → fail fast, typed error").
That split was written before rung 2 had real excerpt rendering behind it, and
it draws the line in the wrong place. The discriminator is not *did we pay*, it
is **do we hold citable evidence**:

```
evidence exists  →  200, degraded=true, excerpts, meta.reason = provider_degraded | circuit_open
no evidence      →  503 problem+json
```

Breaker-open and retries-exhausted are the same experience from the analyst's
seat, and returning a 503 while holding retrieved, cited passages throws away
the strongest thing in this build in precisely the scenario that gets demoed.
"With the circuit open, the app is still answering with sources" is a better
sentence than "the app returns a clean error."

Fail-fast is preserved and is about latency, not payload: an open breaker still
makes no provider call, sleeps for nothing and spends nothing. Observability
does not need the 5xx either — `degraded`, `meta.reason`, `/healthz` and the
`breaker_open` log line all report it, and each is more precise than a status
code shared with four other conditions.

### 7. Three provider defaults are wrong for us, and all three are pinned

**`AsyncOpenAI(max_retries=0)`.** The SDK retries twice by default; left on, our
"max 2 retries" is silently 6, our budget arithmetic is fiction, and the cost
ceiling is breached by a layer we did not write. This single keyword is the
difference between the policy being real and being decorative.

**`reasoning.effort = "none"`, set explicitly.** Reasoning tokens bill as output
— US$4.50/M — and inflate both halves of the constraint at once: cost at the
output rate and latency against an 8 s p95. For this task they buy nothing. The
evidence is already retrieved and delimited; the model's job is to select from
it and cite, not to deliberate. `none` is today's default, which is exactly why
it gets written down: an inherited default can change under us, and this one
would change the unit economics silently. If the evals ever show a gap on the
multi-hop cases, `low` gets tested on those cases specifically, not globally.

**`max_output_tokens`, and it lives in `ResilienceConfig`.** The model will emit
up to 128,000 output tokens. At US$4.50/M that is **US$0.58 from a single
call** — eleven times the per-question budget — and the ledger as designed only
gates *retries*, so nothing in the plan so far stops it. That is a real hole: we
had a hard time ceiling (the deadline) and no hard cost ceiling.

800 tokens is generous for a cited answer in this schema. It sits in
`ResilienceConfig` next to the budget values rather than in the adapter, because
it is the same kind of thing as the deadline and it belongs where a reviewer
looks for spending limits. The decorator passes it down per call, exactly as it
does `timeout_s` — so `max_output_tokens: int | None = None` joins the
`LLMProvider.complete` signature under the same ownership rule, and the same
one-line statement of that rule goes into `.cursor/rules/10-llm.mdc`.

Truncation is handled by failing closed, not by retrying: a response cut at the
cap is invalid JSON, `_parse_draft` already turns that into a refusal, and
retrying would truncate again at full price. The log line names
`finish_reason=length` so a cap that is actually too small is visible rather
than mysterious.

`Usage` gains `reasoning_tokens`, charged at the output rate. With effort pinned
to `none` it should always be zero — which is the point: it is the measurement
that proves the pin is in force, and a non-zero value in `EVALS.md` would mean
the default moved.

### 8. Chaos wraps a real provider and draws once

`ChaosProvider(inner=FakeProvider())` — a non-failing call still returns a
grounded, citable answer, so the outage demo shows recovery and not just noise.
One uniform draw per call, not two independent ones, so `CHAOS_TIMEOUT_RATE=0.3`
plus `CHAOS_500_RATE=0.2` means exactly 50% failures and the rates compose the
way an operator reading `.env` expects. `CHAOS_LATENCY_MS` is applied first and
capped at the deadline the decorator handed down — past that it raises
`ProviderTimeout` rather than sleeping through the budget. `CHAOS_SEED` is
added so the demo is reproducible.

## The ladder, end to end

```mermaid
flowchart TD
  ask["ask.py: llm.complete(messages, schema)"] --> breaker{breaker state}
  breaker -->|open| rung3["rung 3: CircuitOpen. no call, no sleep, no spend"]
  breaker -->|half-open, probe already claimed| rung3
  breaker -->|closed, or the one half-open probe| budgetcheck{"remaining_s > min_retry_budget_s?"}
  budgetcheck -->|no| degraded
  budgetcheck -->|yes| call["wait_for(provider.complete(timeout_s=remaining))"]
  call -->|ok| rung0["rung 0: charge ledger, close breaker, return Completion"]
  call -->|InvalidRequest| raise400["raise unchanged, breaker untouched"]
  call -->|retryable| gates{"attempts left AND time left AND cost left?"}
  gates -->|yes| backoff["rung 1: sleep random * min(base * 2^n, cap)"]
  backoff --> budgetcheck
  gates -->|no| degraded["rung 2: ProviderDegraded"]
  rung3 --> render
  degraded --> render{"evidence retrieved?"}
  render -->|yes| excerpts["200: excerpts + citations + banner, degraded=true, meta.reason=code"]
  render -->|no| problem["problem+json 503"]
  raise400 --> problem
```

`cached_prompt_tokens` is a subset of `prompt_tokens`, so the ledger charges
`(prompt - cached)` at the input tier and `cached` at the cached tier.
`reasoning_tokens` are charged at the output tier alongside
`completion_tokens`.

### What a question actually costs, and what threatens it

A grounded question is roughly 4k input tokens (system + five evidence chunks +
history) and well under 800 output: about **US$0.007**, seven times inside the
envelope. The budget is not threatened by normal traffic. It is threatened by
one runaway generation at US$0.58, which is why the cap is a config value with
a test on it rather than a comment.

**Data residency, noted now because it moves the model, not the code.** Regional
processing endpoints carry a 10% uplift: US$0.825 / US$0.0825 / US$4.95 per
million. InsurCo is a Brazilian insurer whose own corpus contains
`POL-LGPD-2024`, so residency is a plausible client requirement rather than a
hypothetical. At the uplifted rate a question is about US$0.008 — still
comfortably inside US$0.05, so the answer is "yes, and here is the number"
rather than a renegotiation. `DECISIONS.md` records it for the same reason the
prices are config: the day someone asks, the arithmetic already exists.

## Structured logging — the asymmetry, made mechanical

Every failure produces one JSON line carrying `event`, `trace_id`, `model`,
`prompt`, `attempt`, `upstream_status`, `error_code`, `latency_ms`. The response
body carries `type`, `title`, `status`, `detail`, `trace_id` and nothing else.
The mechanism is that the sensitive fields live in `InsurCoError.context`, which
the handler passes to `logger.warning(..., extra=...)` and never touches when
building the body — so leaking one would take a deliberate edit, not an
oversight. Events: `llm_attempt`, `llm_retry`, `llm_degraded`, `breaker_open`,
`breaker_half_open`, `breaker_closed`, `typed_error`, `unhandled_error`.

The prompt is safe to log because the corpus is redacted at ingest and claims
projections exclude identifiers; if that ever stops being true, this line is
where it bites, and it is written down here for that reason.

## Behaviour S5 must exhibit

1. A timeout is retried, the second attempt's `timeout_s` is strictly smaller
   than the first, and the user sees a safe message.
2. Three consecutive failures produce exactly three provider calls — one plus
   two retries — then a degraded response.
3. A 400 produces exactly one provider call.
4. After N consecutive failures the provider is not called at all; after the
   reset window exactly one probe is allowed, no matter how many requests
   arrive at once.
5. Provider down with retrieval up returns HTTP 200, `degraded: true`,
   `meta.reason`, the banner, and citations that resolve to retrieved evidence
   — and so does an open breaker.
6. With no evidence in hand, the same failures are a 503 `problem+json`.
7. A retry that would breach US$0.05 does not happen, and a retry with less
   than `min_retry_budget_s` left does not happen.
8. No single call can spend more than `max_output_tokens` allows, and the
   adapter cannot be edited into dropping the cap without a test going red.
9. Error bodies contain no model name, prompt or traceback; the log line for the
   same failure contains the model name and the prompt.
10. `GET /healthz` reports the breaker state and is the only place the outage is
    a status rather than an inference.
11. `LLM_PROVIDER=chaos` with rates set exercises every rung without a key.
