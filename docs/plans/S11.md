## F4 — the live path is broken. Fix it first.

**Why first:** nothing downstream can be measured live until this lands, and it is the
only defect on this list that silently corrupts *correct* behaviour into a refusal.

`app/llm/openai_provider.py:80` sends the JSON schema with `"strict": False`. Against the
live model this is non-deterministic: **measured 1 of 3 calls conformant**; the other two
returned the JSON *Schema itself* echoed back (top-level keys `["type","properties",
"required"]`). `_parse_draft` (`ask.py:255-259`) catches the resulting `ValidationError`
and returns `Draft(outcome="refused", answer=_CITATION_REFUSAL)` — so a working answer
becomes a user-visible refusal that blames citation validation.

**Measured fix: `"strict": True` plus a strict-shaped schema → 5 of 5 conformant.**

### Edits

1. `app/llm/openai_provider.py:80` — `"strict": False` → `"strict": True`.
2. `app/services/ask.py` `DRAFT_SCHEMA` (31-49) — add `"additionalProperties": false` to
   both objects, and add `"citations"` to `required` (strict mode requires `required` to
   list every key in `properties`).
3. `evals/judge.py:32-40` `VERDICT_SCHEMA` — **same reshape, same commit.**
4. `app/llm/prompts/system.md:16` — "Respond using the given JSON schema." →
   *"Respond with a JSON object that conforms to the given schema."*
5. `app/services/ask.py` `_parse_draft` — stop collapsing a provider-contract failure into
   a citation refusal. Raise a new `ModelContract` error (`app/domain/errors.py`) so the
   turn fails honestly instead of lying about why.
6. `app/api/errors.py` — add `model_contract` to `_STATUS`, `_TITLES`, `_DETAILS`.

### Traps

- **`strict` is not scoped to `DRAFT_SCHEMA`.** It applies to every schema the adapter
  sends. `evals/judge.py:32-40` has no `additionalProperties: false`; leaving it makes the
  judge run die with a 400 → `InvalidRequest` → `judge_run.py` exits 2 and the four
  `grade: judge` golden cases stay ungraded. Fix both schemas or neither.
- **Do not make `citations` nullable** (`"type": ["array","null"]`) as the usual
  strict-mode "optional field" workaround. Measured: `citations: null` fails `Draft`
  validation and reproduces the exact spurious refusal being fixed. An empty array is the
  correct representation.
- **`answer` is already in `required`** (`ask.py:48`). Making it required is a no-op;
  `citations` is the only semantic change.
- **A new error code without a `_STATUS` entry silently becomes 500.** `errors.py:141` is
  `_STATUS.get(code, 500)`.
- Do not bolt a `strict` assertion onto `test_adapter_always_sends_output_cap_and_reasoning_none`
  — it calls `complete(MSGS)` with **no** schema, so `body["text"]` does not exist. KeyError.

### Consequences to record, not to suppress

`PROMPT_VERSION` moves from `4adf882fbe66` to `d660eb1e6005` (both computed). This is by
design — `_prompt_version()` hashes the system prompt plus the schema precisely so a
prompt change invalidates replays. No migration, no cassette, and
`test_prompt_version_is_a_stable_hash` recomputes rather than pinning a literal, so it
stays green. **`DECISIONS.md:554` states the old value as fact — update it.**

**Trap — do not write `d660eb1e6005` into `DECISIONS.md` if you also reword `system.md` in
the same commit.** `ask.py:127` hashes `_system_prompt() + json.dumps(DRAFT_SCHEMA)`, so
editing the prompt produces a *third* value and the literal you just wrote is wrong on
arrival. Land the schema edit, compute the hash, then write it — or make all prompt-affecting
edits first and compute once at the end.

**Trap — `_parse_draft` raising instead of refusing converts truncation into a 502.** Today an
`incomplete` response (the 800-token cap at `openai_provider.py:66`) yields partial non-JSON,
`parsed=None`, and a graceful 200 refusal. After edit 5 that becomes a hard failure. Either
distinguish truncation from a schema echo, or accept the change deliberately and say so.

**Trap — the new diagnostic will be silently dropped by the logger.** `JsonFormatter`
(`app/api/errors.py:58-74`) builds its payload from six fixed fields plus `_LOG_CONTEXT_KEYS`
(`:48-55`). A key not on that list never reaches the log. Add it.

**No offline signal exists for the only failure mode that matters.** The suite passes
identically with and without this change — verified. `jsonschema` is not in `pyproject.toml`
and `FakeProvider` discards `schema` entirely (`fake.py:67`). So write (a) an adapter test
asserting `body["text"]["format"]["strict"] is True` when a schema is passed, and (b) a
recursive invariant test over `DRAFT_SCHEMA` asserting every object has
`additionalProperties: false` and `required == list(properties)`. **Neither substitutes for
the 10-call live gate below.**

## F1 — the degraded path ships policyholder names

`app/services/ask.py:361-373`: the `except (ProviderDegraded, CircuitOpen)` handler calls
`excerpts_answer(evidence)` directly and **never calls `judge()`**. No PII gate, no
sufficiency gate, no ambiguity gate. Proven by execution: a PII question during an outage
returns `outcome="answered"`, `degraded=True`, with the policyholder's full name intact in
the citation snippet. `redact()` strips CPF, phone and e-mail but **cannot match a name**.

This violates the brief's requirement 3 inside the scenario of requirement 5 — the
highest-weighted criterion.

### The correction to the obvious fix

The obvious fix is to call `grounding.is_pii_request(content, evidence)`. **That is not
enough**, and the audit measured why: `is_pii_request` is an *AND* of question-shape and
evidence-shape (`grounding.py:79-81`). A **neutral** question over the same minutes chunk
still ships two policyholder names during an outage — measured, names present in the body.

On the *answered* path the AND is defensible: `judge()` has `redact()` and the sufficiency
gate behind it. On the *degraded* path there is no model answer at all — the entire payload
is raw retrieved text — so the question-shape half of the AND is meaningless.

**Use `grounding.evidence_carries_pii(evidence)` alone on the degraded path.**

### Edit

Inside the `if evidence:` block, before `complete_turn`:

```python
degraded_answer = (
    Answer(outcome="refused", text=_PII_REFUSAL, citations=[])
    if grounding.evidence_carries_pii(evidence)
    else excerpts_answer(evidence)
)
```

`content`, `evidence`, `Answer`, `grounding` and `_PII_REFUSAL` are all already in scope.
Do not retype the refusal string — `judge()` at `ask.py:183-184` is the other call site of
the same rule and the two must stay identical.

Return `citations=[]`, matching every other refusal and what the UI, the eval harness and
the durable store all expect.

### Traps

- **The gate must live INSIDE `if evidence:`.** Above it, it puts a refusal branch on the
  no-evidence path, which `tests/test_degradation.py:73-95` pins as 503 problem+json.
- **Do NOT widen `except (ProviderDegraded, CircuitOpen)` to catch `ProviderUnavailable`.**
  This is the most likely wrong turn: you write the new test against the conftest fixtures,
  get 503 instead of 200, and "fix" the except clause. That flips `T-10`
  (`test_api_messages.py:87-148`) and `T-36` (`test_history_api.py:23-44`) to the wrong
  behaviour. The correct fix is the test's wiring, not the handler's.
- **The shared `app`/`client` fixtures can never reach this branch.** `conftest.py:68-70`
  hands `create_app` the raw `FakeProvider`, whose exception is caught by
  `except InsurCoError` at `ask.py:376` → 503. Wrap in `ResilientProvider` (pattern at
  `test_degradation.py:21-25`) or enqueue a `ProviderDegraded` instance directly.
- `FIXED_CHUNKS` carries no PII, so a new test must use
  `InMemoryRetriever(MINUTES_CHUNKS)` from `tests/test_grounding.py:156-169`.
- **Anchor the edit on the `excerpts_answer(evidence),` argument, not on line 361.** F4 adds
  lines above this handler and shifts it. Every line number in this document is from
  `cc33aa6` and drifts as fronts land.
- **The stated reason the new test needs its own app is subtly wrong, and the wrong reason
  leads to the wrong fix.** `llm.enqueue(ProviderDegraded())` on the conftest `FakeProvider`

  blocker is the conftest retriever, which carries no PII. Believing "the fixtures can never

- **F1 leaves PII at rest, not just in one response.** Measured before the fix: the names come

`ask.py:207` redacts `answer.text` only when the outcome is `answered`. The refused and

**Patch site: the two early returns of `validate_citations` (`ask.py:156-163`).** That is

## F2 — sufficiency is unreachable. But the obvious fix is wrong.

**The bug.** `judge()` checks `is_ambiguous` (189) before the sufficiency gate (201), so
for any question whose evidence spans more than one product and which names none, the
sufficiency gate is unreachable. gs-008 returns `needs_clarification` where the brief
requires `refused`.

**The obvious fix — swap the two blocks — is wrong, and the audit measured three reasons:**

1. **It breaks `au-004`.** `evals/authored.json` case au-004 ("Qual é a franquia da
   cobertura de vidros na minha apólice?") carries `expect_outcome: needs_clarification`
   and passes today. Under a bare reorder it becomes `refused` →
   `boundary_pass_rate: 1.00` (`thresholds.yaml:30`) is a **registered submission
   blocker**, and it also violates `combined_min_precision: 1.00`, since by the file's own
   definition a clarification turned into a refusal is a false refusal.
2. **It does not reliably fix gs-008 anyway.** `ask.py:186-187` returns the model's own
   `needs_clarification` *before both gates*, and `system.md:13-14` explicitly instructs
   the model to emit `needs_clarification` when "it names no product and the evidence spans
   more than one" — gs-008's exact shape. A prompt-compliant live model hits the passthrough
   and the reorder is a no-op.
3. **A supported-but-non-answering draft survives it.** Measured: a draft scoring 1.000 on
   sufficiency falls straight into `is_ambiguous` and returns `needs_clarification`.

**Also measured: the existing 79-test suite passes identically under both orders.** No test
distinguishes them. That is why the bug survived, and it is the whole argument for the
order-pinning tests below.

### The proposed fix — a two-set discriminator, and the reason it cannot be validated offline

Refuse only when the answer is unsupported by the **entire retrieved set**. When it is
unsupported by the *cited* chunk but supported by the retrieved set, and the question is
ambiguous, **ask**.

```python
unsupported_by_cited  = not grounding.is_supported(text, cited)
unsupported_by_corpus = not grounding.is_supported(text, evidence)
```

On *realistic* drafts the discriminator separates the two cases cleanly:

| case | ratio(cited) | ratio(retrieved) | verdict |
|---|---|---|---|
| au-004 "A franquia da Cobertura de Vidros é de R$ 150,00." | 0.667 | 1.000 | ask |
| gs-008 "O desconto para pagamento à vista é de 5%." | 0.000 | 0.000 | refuse |
| gs-009 "O limite da Cobertura de Vidros é de R$ 5.000,00." | 1.000 | 1.000 | answer/ask |

> ### ⚠ Those numbers do not describe the harness that grades these cases.
>
> **`FakeProvider` emits one canned sentence — "A vigência padrão é de 12 meses."
> (`app/llm/fake.py:12`) — whose content terms are `{vigencia, padrao, meses}`. Measured
> against the glass evidence: ratio(cited) = 0.000 AND ratio(retrieved) = 0.000.**
>
> So under **any** ordering that puts sufficiency before ambiguity — bare reorder or
> discriminator alike — gs-009 and au-004 both return `refused` in the fake-driven harness.
> The table above was computed on hypothetical realistic answers that the fake never
> produces. **The discriminator does not save au-004 offline. Nothing does.**
>
> The 0.667 figure is additionally a *fixture artefact*: `tests/test_grounding.py:119-121`
> drops a sentence the real corpus chunk carries
> (`evals/corpus_txt/01_cgauto.txt:240-241`), and the ratio changes on the real text.
> Recompute against the indexed chunk, never against the fixture.

**What this actually means.** The fake-driven evaluation cannot grade the ordering question
at all. Today's green `needs_clarification` results exist because the ambiguity gate
short-circuits *before* the model's (irrelevant) answer is ever examined. That is a property
of the degenerate double, not evidence about the shipped system — and it quietly weakens
`EVALS.md`'s claim that the clarification behaviour is "a genuine measurement of the shipped
system". The PII and citation-forgery cases are unaffected: they do not depend on draft content.

**Therefore: F2 must be validated against the live model, and only after F4.** That is now
possible — the key works and F4 makes structured output deterministic. Concretely:

1. Land F4 first.
2. Re-measure the three cases above with **live drafts** over the **Postgres-indexed** corpus
   (not the in-memory fixture, which lacks the chunks the ratios depend on).
3. Only then choose between the bare reorder and the discriminator, on evidence.
4. Run the boundary suite live. `boundary_pass_rate: 1.00` under `FakeProvider` is not
   achievable with any sufficiency-first ordering, and lowering it to accommodate a
   degenerate double would be exactly the move `thresholds.yaml` forbids.

## F3 — the claims tool is built, tested, and not connected

`app/services/ask.py` contains no reference to `app.tools`. The only importers are
`tests/test_claims.py` and `scripts/gs007_from_db.py`. This leaves the brief's build item 4
("query the claims database as a tool") unmet and half of requirement 1 ("document and
section, **or database query**") unreachable. gs-007 fails all three of its assertions.

The capability is real — `python -m scripts.gs007_from_db` already prints
`paid_amount: R$ 100.000,00`, the citation string
`claims.get_claim_payment(claim_number="SIN-2025-004512")` and a freshness line
`dados até 2026-02-11`. **This front is wiring, not new capability.**

### Design: a deterministic router, not model tool-calling

New `app/services/claims_router.py`: regex on claim id (`SIN-\d{4}-\d{6}`) and policy id,
plus intent keywords, producing an optional list of `(query_name, params)` plans.

Chosen over a model plan/execute round trip because it changes no Protocol, costs no second
model call inside the US$0.05 ceiling, and is testable without the LLM — which is the
architectural line the whole project already holds. There are six named queries, not an
open action space. Record this reasoning in `DECISIONS.md`; it is a question you will be
asked in the technical conversation.

`ClaimsTool.execute()` already returns a fully-formed domain `Evidence`
(`source_kind="claims"`, `doc_role="database"`, `section=citation_call(...)`,
`effective_date=coverage`), so everything downstream — citation validation, rendering,
persistence — already works.

### Trap: route BOTH queries, or gs-007 fails for a new reason

Measured sufficiency ratios for gs-007:

| evidence | ratio |
|---|---|
| corpus only | 0.692 |
| + `get_claim_payment` | 0.769 ❌ still below 0.8 |
| + `get_claim` | **0.846** ✅ |

Routing only `get_claim_payment` leaves the ratio at 0.769 < `SUFFICIENCY_MIN` 0.8, so
gs-007 returns `_UNSUPPORTED_REFUSAL` while its `must_cite` set is satisfied — a failure
that looks like success. The 0.077 that closes the gap comes from `_claimed()`'s Portuguese
label at `claims.py:248-251`.

### Trap: the claims Evidence barely moves the sufficiency needle

`content_terms()` drops every `.isdigit()` token, so `R$ 100.000,00` contributes **nothing**
to the supported set. `get_claim_payment`'s content vocabulary is almost entirely English
field names — only `pago` and `concluido` are Portuguese. A fluent Portuguese answer was
measured at 0.533. Expect to widen the routed evidence rather than to tune the threshold;
moving `SUFFICIENCY_MIN` to make one case pass is the move `thresholds.yaml` forbids.

### Trap: the prompt tells the model the database row is corpus text

`_format_evidence` (`ask.py:236-241`) wraps everything in `<retrieved_corpus>` followed by
the literal sentence "The following is retrieved corpus content", and `system.md` reinforces
it. A claims row arrives labelled as corpus. Fix the wrapper or add a per-item source label;
otherwise the citation the brief asks for ("document and section, **or database query**")
is presented to the model as the wrong kind of thing.

### Trap: `validate_citations` is all-or-nothing over an opaque id

`ask.py:167-170` — if **any** cited `evidence_id` fails to resolve, the entire answer is
replaced by `_CITATION_REFUSAL`. The claims evidence id is an 8-hex digest the model must
transcribe verbatim. One mistyped character turns a correct, well-cited answer into a
refusal. Consider a readable id for tool evidence, or per-citation dropping instead of
whole-answer rejection — and pin whichever you choose with a test.

### Trap: F2 and F3 edit the same function

F2's discriminator adds a second sufficiency test over the **entire retrieved set**; F3
**changes what that set contains** by prepending tool evidence. Landing F3 after F2 silently
changes F2's semantics. Sequence them, and re-run F2's tests after F3 lands.

### Threshold honesty

`thresholds.yaml` forbids revising a threshold after seeing results. Raising

## F5 — the eval harness cannot produce an honest live verdict

### The trap that would fabricate a live run

**`run_golden`'s conversation ids and idempotency keys are stable across invocations, and
idempotency is persisted in Postgres.** Re-running the live tier against the existing
database **replays the committed fake answers**, stamps them `provider="openai"`, and
`report.py:121` — which computes liveness from `meta.provider` alone — renders 30 replayed
fake turns as a live run and prints **PASS** on `US$0.0000`.

Zero spend, zero network, a completely fabricated result that looks like the real thing.
**Reset the conversations or mint fresh ids before any live run.** This is the single most
dangerous step in this plan.

### Other blockers, all measured

- **No `load_dotenv()`** in `app/main.py`, `run_golden.py`, `judge_run.py` or `boundary.py`.
  With the key only in `.env`, `AsyncOpenAI()` raises at *import* of `app.main` and uvicorn
  dies with a message that looks nothing like "missing key". Export the key in the shell or
  add the call.
- **`report.py:215` crashes** with `TypeError` when any record has `outcome: None` — i.e.
  on any non-200 response. One provider error in 30 and `EVALS.md` cannot be generated.
  Fix: `sorted(str(o) for o in outcomes)`.
- **One record without a `meta` block flips `live` to False** and prints the whole "Tier 2
  did not run … the key has no credits" block against a real live run.
- **`RETRIEVER_ARM=hybrid` over a `--no-embed` corpus is identical to lexical** — the `vec`
  CTE is gated on `embedding IS NOT NULL`, so the join degenerates — while paying an
  embedding call per question. Either re-ingest with embeddings or stay on lexical and say so.
- **Query-embedding spend never enters `QuestionBudget`** (`EmbeddingCache` bypasses
  `ResilientProvider`), so a non-lexical arm publishes a cost per question that omits a real
  charge. Stay lexical, or state the omission in the generated file.
- **`run_golden` overwrites `evals/results/run-{1,2,3}.json`** — the committed keyless
  evidence the current EVALS.md honesty argument rests on. Move them to
  `evals/results/keyless/` first; `report.py:49` globs the top level only.
- **`run_golden` reads `RETRIEVER`/`RETRIEVER_ARM` in the eval process**, independently of
  the API process. Without `RETRIEVER=hybrid` it silently falls back to the two-chunk
  `InMemoryRetriever` and citation validity fails 30/30 for a reason that is not printed.

- **Deleting gs-007 from `expected_failures` must remove the KEY, not empty it.** Leaving
  `expected_failures:` with nothing under it makes `yaml.safe_load` return `None`, and
  `report.py:202` iterates it → `TypeError`. Reproduced.
- **`deterministic_pass_rate` — the headline golden gate — is never rendered by
  `report.py` at all.** The whole `expected_failures` discussion is about a number that does
