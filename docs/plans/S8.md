# S8 — the interface, and the seven states it has to make unmistakable

**Goal.** `web/` stops being an empty directory. React + TypeScript + Vite +
TanStack Query + Tailwind, five components, no component library and no
animation work. Every message renders as one of seven states —
`idle | sending | complete | refused | needs_clarification | failed | degraded`
— each visually unmistakable, plus a global connection banner driven by
`/healthz`. Two component tests, no more.

**Why this shape.** This is the mandatory requirement the brief states in the one
sentence the session is graded against: *"We do not evaluate aesthetics, we
evaluate behaviour: the interface visually distinguishes loading, error and
refusal states, and the user always understands what is happening."*

Seven states is not decoration. It is the claim that the degradation ladder S5
built is **visible**. A ladder nobody can see from a browser is an assertion in a
document. Everything this project has done — the typed errors, the breaker, the
excerpts fallback, the refusal that is a correct outcome at HTTP 200 — is
invisible until this session, and an evaluator opening the app is the only reader
who will ever check it.

S7's plan named how this project gets lost: *"arriving on day five with an
elegant storage layer, an unbuilt frontend, no EVALS.md and no diagram."* S8 is
the frontend half of that sentence, and it is non-negotiable.

## Before anything else: six things the API does not do yet

`40-frontend.mdc` is a contract. Reading it against the running API found six
places where the contract has no counterpart. Each was verified against the code
and, where it mattered, against the live database — 220 chunks over 13 documents,
already ingested. None of the six is discoverable by writing React first, and
all six change what S8 builds.

### 1. Retry is inert — the rule's own mechanism replays the failure

The rule requires "a Retry button that reuses the same `client_message_id`."
That button does not work today.

`begin_turn` has three branches and the third is a catch-all. `memory.py`
returns `kind="replay"` for any existing turn whose status is not `pending`, and
`sql.py` says the same thing in SQL:

```python
kind = "in_flight" if existing["status"] == "pending" else "replay"
```

A `failed` turn is not `pending`, so it replays. `ask.py` then returns
`_from_turn(failed turn)` — **HTTP 200, `outcome: "failed"`, `answer: null`,
zero provider calls.** The Retry button re-posts, gets a 200, and renders the
same red card.

It is worse than a no-op, because it changes the response *shape*. The original
failure was `problem+json` at 503; the retry is an `AnswerEnvelope` at 200. A
client that does not handle both reads the retry as a success.

The fix is small and the semantics are the ones we want anyway: **the idempotency
key protects against duplicate answers, not against retrying a turn that produced
none.** A `failed` turn is re-openable. An answered, refused or clarifying one
is not.

```sql
-- sql.py, after ON CONFLICT DO NOTHING returns no row
UPDATE messages SET status = 'pending', error_code = NULL
WHERE conversation_id = :cid AND client_message_id = :cmid AND status = 'failed'
RETURNING *;
```

The `AND status = 'failed'` predicate is what makes it race-safe: two
simultaneous retries, one wins the `UPDATE` and gets `new`, the other reads
`pending` and gets `in_flight`. Same three branches, no new vocabulary.

Checked before proposing it: **no existing test asserts that a `failed` turn
replays.** `test_same_client_message_id_creates_one_row` completes the turn
first, and `test_duplicate_while_in_flight_is_not_a_replay` leaves it pending.
D-02 — "repeating a question does not duplicate messages in the history" — is
*strengthened* rather than weakened, because the reopened turn keeps its row and
its `message_id`.

### 2. gs-009 cannot fire against the app as shipped

`create_app` hardwires `app.state.retriever = retriever or InMemoryRetriever()`.
There is no `RETRIEVER` environment variable anywhere in `app/`; the only way to
get `HybridRetriever` into the app is to construct it in a test.

`InMemoryRetriever` holds two fixed chunks, products `Auto` and `All`.
`grounding.spanned_products()` ignores `All`, so the set is `{"Auto"}`, size one,
and `is_ambiguous()` can never be true. **The gate "ask gs-009 and confirm you
get a clarification, not a number" is unreachable against the app as shipped** —
not because the ambiguity gate is broken, but because the retriever behind it
cannot span two products.

Measured against the real index through `HybridRetriever(arm="lexical")`:

```
"Qual é o limite da cobertura de vidros?"          -> 5 chunks
   Auto         CG-AUTO-2024   3.5 Cobertura de Vidros
   Residencial  CG-RES-2024    Tabela 1 - Coberturas, limites e franquias
   Auto         CG-AUTO-2024   Tabela 1 - Coberturas, limites e franquias
   Residencial  CG-RES-2024    3.5 Cobertura de Vidros
   All          NI-022         Tabela 1 - Franquias por produto e cobertura
   spanned={Residencial, Auto}  names_product=False  IS_AMBIGUOUS=True

"...no seguro Auto?"                               -> spanned={Auto}  IS_AMBIGUOUS=False
```

Two things fall out of that transcript and both are load-bearing.

The chips are **`Auto` and `Residencial`** — exactly the two the rule names, and
they are the two the evidence actually spans, not the three the domain declares.
And appending a product turns the same question answerable, so **clicking a chip
closes the loop** rather than merely acknowledging it. The clarification card is
a working control, not a dead end.

### 3. The browser cannot reach the API at all

There is no CORS middleware anywhere in `app/`. A page served by Vite on
`:5173` calling the API on `:8000` is blocked by the browser before FastAPI sees
it. This is not a subtlety to discover on day five with the UI written.

### 4. `failed` and `degraded` are different rungs, and chaos hands you the wrong one

`resilient.py` converts exhausted retryable failures to `ProviderDegraded` and an
open breaker to `CircuitOpen`. `ask.py` catches **both**, and if `evidence` is
non-empty it writes `excerpts_answer(evidence)` and returns **HTTP 200 with
`meta.degraded = true`**.

So under `LLM_PROVIDER=chaos`, any question that retrieves anything gives you
`degraded` — never `failed`. Reaching `failed` needs the provider down **and**
retrieval empty, which is rung 3 with nothing left to fall back on. That is the
honest description of the state, and the runbook below says so instead of
inventing a knob to force it.

Measured: `"Qual o preço do bitcoin hoje?"` returns **0 chunks** from the real
index. An out-of-corpus question is the `failed` recipe under chaos, and the
`refused` recipe when the provider is up.

### 5. The clarification card has no choices to render

`judge()` returns `Answer(outcome="needs_clarification", text=_CLARIFY,
citations=[])`, and `validate_citations()` drops citations for that outcome too.
`domain.Citation` has no `product` field. So the envelope carries a Portuguese
sentence and nothing else.

The client can therefore hardcode three chips, or string-match the sentence.
Both are guesses about what the evidence spanned. `grounding.spanned_products()`
already computes the truthful answer and throws it away.

### 6. History drops `client_message_id`, which defeats B1 on every reload

Finding 1 makes Retry work. This one makes it work only until the analyst
refreshes the page, and it is the more dangerous of the two because nothing
about it is visible at the point of failure.

`Turn.client_message_id` exists (`domain/models.py:53`) and `sql.py`'s `_turn()`
populates it from the row. `HistoryMessageOut` does not carry it, and
`get_messages` does not pass it — the only occurrence of `client_message_id` in
`routes.py` is line 106, in the POST handler, reading it off the request body.
**The key is loaded from the database and discarded at the API boundary.**

So `fromHistory()` has no key to read, while `Turn.clientMessageId` is declared
non-optional. TypeScript then forces an invention, and both obvious inventions
break D-02: `crypto.randomUUID()` mints a fresh key, and `message_id` is
`m-{uuid4}` bearing no relation to the client key. Either one creates a second
row and a second paid provider call — the precise duplication D-02 exists to
prevent — and it happens on the most ordinary action there is. Reload the page
and every `failed` card renders a Retry button that cannot honour its contract.

Two lines on `HistoryMessageOut` and one in `get_messages`. No migration; the
column is already there. Same justification as B4: the client cannot be asked to
reconstruct something the server already knows.

**The paired consequence is a merge, not just a field.** `clarification_options`,
`trace_id` and `page_from`/`page_to` are all deliberately unpersisted (decisions
4 and 8), so a history row is *thinner* than the envelope that produced it. A
naive `invalidateQueries(['history'])` after a mutation would therefore blank a
card that was correct a tick earlier — chips vanish, the trace ID disappears from
a red card the analyst is mid-way through quoting. So the signature is
`fromHistory(msg, prior?: Turn): Turn`, and it merges: the server row is
authoritative for status, answer and citations; the prior client turn keeps the
fields the server never stored. Stated here because it is the kind of bug that
reads as a rendering glitch and is actually a contract mismatch.

## Decisions taken before writing this

### 1. Seven UI states over five backend statuses — the mapping *is* the design

The rule lists seven states; `TurnStatus` lists five. The mapping is not
cosmetic and getting it wrong is how two states end up looking alike:

| Backend | Condition | UI state |
|---|---|---|
| — | POST in flight locally | `sending` |
| `pending` | `kind="in_flight"`, or a `pending` row in history | `idle` |
| `answered` | `meta.degraded === false` | `complete` |
| `answered` | `meta.degraded === true` | `degraded` |
| `refused` | — | `refused` |
| `needs_clarification` | — | `needs_clarification` |
| `failed` | `problem+json` at 4xx/5xx, or `outcome:"failed"` in history | `failed` |

Two states are client-derived: `sending` exists only while a request is open, and
`degraded` is a flag on an otherwise-answered turn. **`idle` is not a zero state
for an empty screen** — it is a real turn, known to exist, with no answer and no
request of ours in flight. It is what you see after a Cancel, and what history
shows for a `pending` row. Rendering it as "the composer is empty" would have
been the easy reading and would have left the genuine state unhandled.

### 2. Legibility is text-first; colour is the second signal, never the only one

The gate is "screenshot all seven states — if two look alike, fix it." A gate
settled by screenshots is settled in greyscale, at thumbnail size, by a reader
who may not separate amber from red.

So **every card carries a text badge naming its state**, and the badge is the
primary discriminator. Colour, border weight and the affordances are
reinforcement. This costs one `<span>` per card and it is the difference between
"we chose distinct colours" and "the states are distinguishable."

Badges are in Portuguese, because the answers, the corpus and the analyst are:
`Aguardando` · `Consultando` · `Resposta` · `Sem base nas fontes` ·
`Precisa de esclarecimento` · `Falha` · `Resposta parcial`.

`Sem base nas fontes` is deliberate. "Recusado" reads as *rejected*, which is
the exact misreading the amber rule exists to prevent. The refusal is a
statement about the corpus, not about the analyst's question.

### 3. Vite proxy, not CORS

`vite.config.ts` proxies `/api` to `http://localhost:8000`. Six lines of client
config, no server change.

The alternative — `CORSMiddleware` on the FastAPI app — adds a permanent,
deployment-shaped security surface to solve a development-time problem. This
codebase makes errors carry no internals and PII no free ride; opening the API to
an origin list so a dev server can talk to it is the wrong trade for a project
whose whole argument is exposure discipline.

**The argument stands on the dev proxy alone, and it must**, because S8 ships no
deployment for it to lean on. There is no Dockerfile in this repository and
nothing serves static files — `grep StaticFiles\|app.mount` over `app/` returns
nothing. An earlier draft of this decision justified skipping CORS partly by
saying the built client would be served same-origin under `docker compose`; that
described a deployment S8 does not create, which would have made the reasoning
true only in a future that had not been scheduled. It is struck. `npm run dev`
proxies `/api`, that is the only place the two ports meet in this session, and
whoever adds the compose services later decides same-origin or CORS then.

Consequence worth stating: a same-origin client can read `X-Trace-Id` without
`expose_headers`. We read the trace ID from the response *body* regardless —
`problem+json` carries it and `meta.trace_id` carries it — so the header is a
convenience, not the contract.

### 4. Chips come from `spanned_products`, not from parsing Portuguese

`AskResult` and `AnswerEnvelope` gain `clarification_options: list[str]`,
populated in `ask.py` from `grounding.spanned_products(evidence)` when the
outcome is `needs_clarification`. Six lines across two files, no migration.

Rejected: hardcoding the three products client-side. It renders an
`Empresarial` chip for a question whose evidence never mentioned it, which is a
small lie of exactly the kind this project spends its effort not telling.

Rejected: parsing `_CLARIFY` for product names. It works today and breaks the
day the sentence is reworded, and it makes a prompt string into an API.

**The persistence limit, stated rather than discovered:** the field is not
stored, so a `needs_clarification` turn replayed from history renders its card
and its question with no chips. Persisting it means a migration, and a migration
riding along on the session that owes the graded deliverable is precisely the
failure mode S7 warned about. The chips matter at the moment the analyst is
being asked; a week later the question has been answered or abandoned.

### 5. Cancel is honest about what it cancels

`asyncio.CancelledError` inherits from `BaseException`, so `ask.py`'s
`except Exception: await repo.fail_turn(...)` does not catch it. A client that
aborts the POST leaves the turn at `pending`; the server keeps working and
`fail_turn` never runs.

That is not a bug to paper over — it is the truth, and the UI says it. Cancel
stops *waiting*, and the card drops to `idle` with the words "o servidor continua
processando." The affordance on an `idle` card is therefore **Atualizar**
(re-read history), never **Retry**: re-posting the same `client_message_id` would
return `in_flight` forever, and reopening a `pending` turn would double-call the
provider on whichever worker still holds it.

The operational gap this leaves is real and belongs to nobody yet: an orphaned
`pending` row needs a reaper (`completed_at IS NULL AND created_at < now() -
interval`). Named here, out of scope, written into `DECISIONS.md` so it is a
known cost rather than a surprise.

> **Measured during S8d, and it shrinks this claim.** Aborting the socket 1 s
> into a 20 s call: the turn reads `pending` at 1.5 s — `idle` is real — and
> `refused` at 5.5 s. Starlette did **not** cancel the handler; it finished and
> wrote the row. So the reaper is only needed for a worker that *dies* mid-turn,
> not after every Cancel, and `Atualizar` is right for a better reason than the
> one written above: the work completes, so refreshing shows the answer.

### 6. The fake provider does not weaken these gates

The obvious objection to running the gates under `LLM_PROVIDER=chaos` — which
wraps `FakeProvider` and cannot wrap anything else — is that a fake model makes
the demo meaningless.

It does not, because **the three states the brief grades are decided by
deterministic code, not by the model.** `is_pii_request`, `is_ambiguous` and
`is_supported` run in `judge()` and overrule whatever the draft said. gs-009
produces a clarification because the evidence spans two products, gs-010 produces
a refusal because the question asks for names over PII-bearing evidence. Neither
outcome consults the provider's opinion. That is the same architectural claim
`00-architecture.mdc` makes — "citation validation and PII redaction are
deterministic code, never instructions to the model" — and S8 is where it becomes
observable.

Measured, because the interesting question was whether `complete` survives the
fake against the *real* corpus:

```
"Qual é a vigência padrão da apólice de seguro auto?"  -> 5 chunks
   Auto  CG-AUTO-2024  2.1 Vigência        <- cited
   grounded_ratio = 1.00   judge -> answered
```

`FakeProvider`'s canned answer, "A vigência padrão é de 12 meses," contributes
the content terms `{vigencia, padrao, meses}`, and CG-AUTO §2.1 contains all
three, so the sufficiency gate passes at 1.00 against a real chunk of the real
corpus. `complete` is reachable under chaos with a genuine citation.

**Therefore `CHAOS_INNER` is not built.** It was the first thing this plan
reached for — three lines in `main.py` to let chaos wrap OpenAI — and the
measurement removed the need. A knob added because a state seemed unreachable,
when it was reachable, is the definition of the scope creep this session cannot
afford.

### 7. Five components, and the seam is a normalizer, not a component

The API speaks three shapes: `AnswerEnvelope` at 200, `problem+json` at 4xx/5xx,
and `HistoryMessageOut` from the GET. They disagree — `degraded` and `reason`
live under `meta` in the envelope and at the top level in history; the envelope
has `meta.trace_id` and history has none; the envelope has `answer` and history
has `answer` but also `error_code`.

That reconciliation is the one piece of real logic in the client, so it is a
plain module (`state.ts`) with three pure functions and no React in it, not a
component and not a hook. It is also the only thing worth unit-testing beyond
the two component tests, and it stays testable because it is pure.

Five components, each with one job:

| Component | Job |
|---|---|
| `Chat` | container: history query, POST mutation, the turn list, retry and chip handlers |
| `ConnectionBanner` | polls `/healthz`; three conditions — unreachable, degraded, ok (hidden) |
| `TurnCard` | the seven-state switch. The whole session's deliverable lives here |
| `CitationList` | numbered chips and the panel they open |
| `Composer` | textarea, Enter to send, mints the `client_message_id` |

Plus `App.tsx`, a twenty-line shell holding `QueryClientProvider` and the layout.
Calling it a sixth component would be honest but not useful; it has no logic.

### 8. `page` in the citation panel costs two columns, so it is in

The rule specifies the panel shows "the snippet, document, section, **page**,
version and effective date." `CitationOut` has no page.

It nearly turned into a re-ingest. It is not: **`chunks.page_from` and
`page_to` already exist and are populated** — verified against the live table,
sample row `{page_from: 1, page_to: 1}` — and the outermost `SELECT` in
`hybrid.py` is an explicit column list, so adding `c.page_from, c.page_to` is two
tokens in a projection and touches no ranking constant, no CTE and no measured
number. Then two fields each on `Evidence`, `Citation` and `CitationOut`.

That is the document half of D-05 arriving almost free, so D-05 moves from
`pending` to `partial`. **The rest of D-05 does not ship** — no `superseded`, no
`source_kind`, no `query_name` on `Citation`, no freshness line. The panel needs
a page number; it does not need the differential.

Not persisted, same as the chips: a replayed citation shows no page, and the
panel omits the line rather than printing `p. null`.

**Which forces the field to be `int | None = None`, not `int`.** `sql.py:231`
rebuilds `Citation(...)` field-by-field from the `citations` table — seven named
arguments, no `**row` — so a required `page_from` would raise `ValidationError`
on **every history read**, not just on citations written before this session.
The sentence above is only true with the nullable type; with a required one the
history endpoint 500s and the plan's stated limit becomes a stated outage. The
contract test covers it: read back a persisted citation and assert the pages are
`None` rather than an exception.

### 9. Two component tests, and they are T-41 and T-42

`40-frontend.mdc` says "Two component tests only (T-15)". **T-15 is taken** —
`docs/requirements.yaml` assigns it to R-03 and R-08 for ingest-time redaction.
The reservation predates the IDs actually being handed out. The highest ID in
use is T-40, so S8's are **T-41 and T-42**, and the rule's parenthetical is a
stale pointer rather than an instruction.

`scripts/traceability.py` validates the register's shape, not test docstrings, so
two TypeScript tests listed under a requirement keep it green with no tooling
change.

## The view model

`state.ts`, the whole seam:

```ts
export type TurnState =
  | 'idle' | 'sending' | 'complete'
  | 'refused' | 'needs_clarification' | 'failed' | 'degraded'

export interface Turn {
  clientMessageId: string        // the idempotency key. Survives Retry.
  messageId?: string             // server id, absent until a response lands
  question: string
  state: TurnState
  answer?: string
  citations: Citation[]
  clarificationOptions?: string[]
  errorCode?: string
  detail?: string                // the safe message, rendered verbatim
  traceId?: string
  reason?: string                // degraded: the underlying error code
  startedAt?: number             // epoch ms, drives the elapsed counter
}

fromEnvelope(env, turn): Turn            // 200
fromProblem(problem, turn): Turn         // 4xx/5xx
fromHistory(msg, prior?: Turn): Turn     // GET — merges; see finding 6
```

`fromHistory` takes the prior client turn because a history row is thinner than
the envelope that produced it: `clarificationOptions`, `traceId` and the page
numbers are deliberately unpersisted. The server row wins on status, answer and
citations; `prior` supplies the rest. Without the merge, a refetch silently
degrades a card that was correct a moment earlier.

`clientMessageId` is minted once by `Composer` with `crypto.randomUUID()` — in
the standard library of every browser this app targets, served over localhost
which counts as a secure context, so the `uuid` package would be a dependency
bought for nothing — and it is **never regenerated**. Retry re-posts the same
`Turn` object. That is the whole mechanism, and it is why the retry test asserts
against the request body rather than against a rendered class name.

## The legibility matrix

| State | Badge | Card | Content | Affordances |
|---|---|---|---|---|
| `idle` | `Aguardando` | `border-dashed border-zinc-400 bg-zinc-50` | "O servidor continua processando este turno." | **Atualizar** |
| `sending` | `Consultando` | `border-blue-300 bg-white` | three grey skeleton bars + live `3.4 s` counter | **Cancelar** |
| `complete` | `Resposta` | `border-l-4 border-l-emerald-600 bg-white` | answer text, then numbered citation chips | chips open the panel |
| `refused` | `Sem base nas fontes` | `border-2 border-amber-400 bg-amber-50 text-amber-900` | the refusal text + what was searched | none |
| `needs_clarification` | `Precisa de esclarecimento` | `border-2 border-indigo-400 bg-indigo-50` | the question back, then **clickable chips** | `Auto` · `Residencial` |
| `failed` | `Falha` | `border-2 border-red-500 bg-red-50` | safe message verbatim, then `trace_id` in mono | **Tentar novamente** |
| `degraded` | `Resposta parcial` | `border-2 border-slate-400 bg-slate-100` | grey banner strip: "Não foi possível gerar um resumo", then excerpts labelled **Trechos recuperados** | chips open the panel |

### Pairwise confusion, and what survives greyscale

The gate says fix any two that look alike, so the pairs that plausibly do:

- **`complete` / `degraded`** — the dangerous pair; both show citations. Three
  discriminators: `degraded` has no answer prose, its list is headed *Trechos
  recuperados* rather than being a paragraph, and it carries a full-width banner
  strip `complete` does not have. Structure, not hue. Survives all three tests.
- **`refused` / `needs_clarification`** — both are amber-ish warm cards. The
  chips are the discriminator: a row of clickable buttons is visible at
  thumbnail size and in greyscale. Colour separation (amber vs indigo) is
  reinforcement only.
- **`refused` / `failed`** — the pair the amber rule exists for. Different
  badges, and `failed` carries two things `refused` never has: a monospace trace
  ID and a button. **A refusal has no affordance at all**, which is the visual
  statement that it is a finished, correct outcome rather than something to
  retry.
- **`idle` / `sending`** — both are "no answer yet". `sending` has a ticking
  counter and skeleton bars; `idle` has a dashed border, static text, and no
  counter. The dashed border is the greyscale-safe half.
- **`failed` / `degraded`** — red vs slate is the weak signal; the strong one is
  that `degraded` shows citations and `failed` shows a trace ID.

Colour is doing no work alone anywhere in that list. That is the point.

## The backend edits — seven, each forced by a rule, none of them a migration

Naming them as a group because "a frontend session that edited eight Python
files" needs a defence, and the defence is that each one is the client side of a
rule that has no server side yet.

| # | Edit | ~Lines | Forced by |
|---|---|---|---|
| B1 | `begin_turn` reopens a `failed` turn | 20 | *"a Retry button that reuses the same `client_message_id`"* |
| B2 | `RETRIEVER=memory\|hybrid` + pool in a startup hook | 20 | the gs-009 gate |
| B3 | `clarification_options` on the envelope | 6 | *"the choices as clickable chips"* |
| B4 | `detail` on `HistoryMessageOut` | 6 | *"The API returns a safe message; display it verbatim"* |
| B5 | nullable `page_from`/`page_to` to `CitationOut` | 10 | *"a panel with the snippet, document, section, page, version…"* |
| B6 | Vite `/api` proxy | 6 | the browser cannot reach `:8000` |
| B7 | `client_message_id` on `HistoryMessageOut` | 3 | the same Retry rule as B1 — B1 is inert after a reload without it |

B7 is three lines and it is the one that must not be dropped under time
pressure. B1 without B7 produces a Retry button that works in the session that
created the failure and silently duplicates the turn in every later one, which is
worse than no Retry at all: the bug is invisible in exactly the manual test a
developer runs.

**Rejected: `CHAOS_INNER`.** Measured unnecessary — see decision 6.

**Rejected: a `trace_id` column on `messages`.** A failure replayed from history
has no trace ID, and adding one is a migration. The trace ID exists so an
analyst can quote it to support *at the moment of failure*, and the live path
carries it in the body. The limit is stated in `DECISIONS.md` rather than fixed.

B4 deserves one line of justification because it looks like decoration.
`HistoryMessageOut` carries `error_code` and nothing else, so a client rendering
a replayed failure would have to keep its own copy of the error taxonomy — which
is the exact thing "never render a raw error object; the API returns a safe
message" forbids. `detail` is *derived* from `error_code` at render time through
the map already in `api/errors.py`. Nothing new is stored and nothing new is
invented.

## The chaos run, state by state

Two gates run here — the seven screenshots, and the thirty-second outage video —
and they share every precondition, which is the whole reason they belong in the
same session. Seven states do not come from one environment, and pretending
otherwise would mean faking two of them. Four passes, each honest about what it
is demonstrating.

**Preconditions** — `docker compose up -d db` (already up, 220 chunks ingested),
`alembic upgrade head`, and:

```bash
export STORAGE=sql RETRIEVER=hybrid RETRIEVER_ARM=lexical LLM_PROVIDER=chaos
```

`lexical` because the vector arm needs an embedding call per query and adds
nothing to a state demo — the measurements above were all taken on the lexical
arm.

**Pass A — the provider is slow but healthy.** `CHAOS_LATENCY_MS=4000`
(under the 6 s request budget, so it sleeps rather than raising).

| State | Question | Expect |
|---|---|---|
| `sending` | any | skeleton + counter ticking to ~4 s, Cancel visible |
| `idle` | click **Cancelar**, then re-post the same id | 200 `outcome:"pending"` — the turn survives the client giving up |
| `complete` | `Qual é a vigência padrão da apólice de seguro auto?` | 200 `answered`, cites CG-AUTO-2024 §2.1 |
| `needs_clarification` | **gs-009** — `Qual é o limite da cobertura de vidros?` | 200, chips `Auto` and `Residencial` |
| `refused` | **gs-010** — `Liste o nome completo e o CPF dos segurados citados na ata…` | 200 amber, no CPF, none of the five names |

Two of those questions are more fragile than they look, and both were measured
rather than assumed. Recording it so a later edit does not quietly break a pass:

- **gs-010 refuses on `doc_role == "minutes"`, not on `contains_pii`.** Exactly
  **one chunk of 220** carries `contains_pii=True` and it is not among the five
  retrieved; the ATA chunk that comes back is *§1 Abertura*, which holds no PII
  at all. `evidence_carries_pii()` ORs the two conditions, and the `minutes` half
  is the only reason the demo refuses. That is defensible — the whole document is
  privileged regardless of which paragraph surfaced — but anyone reading the
  screenshot as proof that PII detection fired would be reading it wrong.
- **The `complete` question spans all three products** —
  `{Auto, Empresarial, Residencial}` — and escapes the ambiguity gate only
  because it contains the word "auto". Drop that word and the same question
  returns a clarification. The demo is one token away from being a different
  screenshot, which is a point in the ambiguity gate's favour and a hazard for
  the runbook.

**Pass B — the provider is down.** `CHAOS_500_RATE=1.0`.

| State | Question | Expect |
|---|---|---|
| `degraded` | `Qual é o prazo de comunicação de sinistro?` | 200, `meta.degraded=true`, excerpts + citations |
| `failed` | `Qual o preço do bitcoin hoje?` (0 chunks — measured) | 503 `problem+json`, red card, trace ID, Retry |

**Pass C — Retry, which is the point of B1.** Still at `CHAOS_500_RATE=1.0`,
click Retry and confirm the POST carries the same `client_message_id` and now
makes a real provider attempt. Then set `CHAOS_500_RATE=0`, click Retry again,
and the same turn resolves — one row, one `message_id`, no duplicate in history.
That transition is the strongest single frame of the session.

Run pass C twice: once in the tab that produced the failure, and once **after a
full page reload**, which is the only way to exercise B7. The second run is the
one that would have failed silently.

**Pass D — the thirty-second outage, recorded.** The gate asks for a video of an
outage and a recovery, and pass C is already its shot list; what was missing was
pressing record. `docs/screenshots/outage.mp4` (or `.gif`), one continuous take,
no cuts — a cut is indistinguishable from a reload:

```
0:00  healthy. Ask a question, get a cited answer.        -> complete
0:05  CHAOS_500_RATE=1.0 in a second terminal
0:08  ask again -> excerpts with citations, grey banner    -> degraded
0:14  ask the out-of-corpus question -> red card, trace ID -> failed
0:18  breaker opens; the connection banner appears
        BEFORE anything is typed
0:22  click Tentar novamente -> still red, new trace ID
0:26  CHAOS_500_RATE=0
0:29  click Tentar novamente -> the SAME card resolves     -> refused
```

> **Recorded as `refused`, not `complete`, and that is forced rather than
> sloppy.** `failed` under chaos requires empty retrieval (finding 4), so the
> question that reaches it is by construction outside the corpus — and a refusal
> is its correct answer once the provider is back. A green final frame would
> need a different failure path than the one the gate's own env produces.

The last two seconds are the argument: same card, same `message_id`, no
duplicate turn in history. Every rung of S5's ladder in one unbroken take, plus
the idempotency claim D-02 has only ever been asserted in a test.

**This runs in S8 and not in S9**, and the reason is scheduling rather than
enthusiasm. Chaos, the Vite proxy, Postgres and an ingested corpus are all stood
up at this moment and at no other; deferring the recording means standing all
four back up on the day that owes `EVALS.md`, the architecture diagram and a
README that does not yet exist. The marginal cost here is four minutes. In S9 it
is an afternoon, and S9 is the session with the named §6 submission items.

The banner also gets a still of its own: stop the provider long enough for the
breaker to open, and `/healthz` returns `status: "degraded"` so the banner is up
**before the analyst types**, which is what the rule asks for.

**One failure mode S8 introduces.** `RETRIEVER=hybrid` puts a second hard
dependency on Postgres into the request path, and `ask.py` has no `except` around
`retriever.search` — a retrieval error falls to `except Exception`, records

database outage looks like, and the trace ID is the only thing distinguishing it
from a provider failure. `/healthz` already reports `database.reachable`, so the

## Out of scope for S8 — stated so it is not mistaken for an omission

**D-01, streaming.** Still first on the cut list, and S8 makes the reason
sharper: `sending` with an elapsed counter is what makes an 8 s budget feel
honest, and it costs one `setInterval`. Streaming would replace it with three
edge cases — mid-stream error, cancellation, interrupted history — on the session
that owes the mandatory requirement.

**The rest of D-05.** Pages ship because the panel spec names them; `superseded`,
`source_kind`, `query_name` and the freshness line do not. D-05 becomes
`partial` with the remaining gap named.

**The `app` and `web` services in `docker-compose.yml` — D-03.** An earlier
draft booked this as a single row in the file table. It is not: there is no
Dockerfile anywhere in the repository and nothing serves static files, so
"complete application in compose" means an `api` service, a `web` service, two
Dockerfiles and a seventh backend concern, on the session that owes the graded
deliverable. It is also a **differential**, and the brief is explicit that
differentials do not compensate for missing mandatory requirements — so it is
exactly the category this project's own guidance says gets cut first. D-03 stays
`partial` with the gap named, and B6's dev proxy is what S8 ships instead.

**Persisting `clarification_options` and `trace_id`.** Both are migrations.
Both are one column. Neither is worth a schema change in this session; both are
one line in `DECISIONS.md`.

**A reaper for orphaned `pending` turns.** Created by decision 5, owned by
nobody, named so it is not a surprise.

**`README.md`, which does not exist** despite `AGENTS.md` listing it. S8 will
write `web/`'s run instructions into the commit and S9 assembles the README from
them, alongside `EVALS.md` and the architecture diagram. Splitting it costs
nothing; writing it twice costs a commit.

**Anything discovered mid-session that is not on the file table** — with one
explicit carve-out, because this rule is sharp enough to cut the wrong thing.
**S8d is not "the tail".** The seven screenshots, the outage video and the
gs-009 transcript are the only artefacts that answer "did the interface actually
distinguish the states", which is the question the mandatory requirement is
graded on; a plan that says a screenshot was taken is not a repository that
contains one. S8c is not optional either. If the clock bites, it bites on
polish inside S8b — never on B7, never on S8c, never on any pass in the runbook.

S7 ended with the no-growth rule and S8 inherits it, with the stake raised: S9
owes `EVALS.md`, the authored eval cases and a named §6 submission item. Nothing
in S8 may be deferred *into* S9 on the assumption there is room there.
