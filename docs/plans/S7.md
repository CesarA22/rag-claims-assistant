# S7 — persistence, and the history surface it makes possible

**Goal.** `app/storage/` stops being a dictionary. Five tables — `conversations`,
`messages`, `citations`, `documents`, `chunks` — under SQLAlchemy Core with
Alembic owning the schema. `client_message_id` becomes
`UNIQUE (conversation_id, client_message_id)`, so idempotency is a database
constraint rather than a process's memory. `GET /conversations/{id}/messages`
renders history including `failed` turns, and `/healthz` reports the database
alongside the breaker.

**Why this shape.** S1 wrote `ConversationRepository` as one of the four seams
and justified it with a named change: "absorbs the storage change." S7 is that
change, and it is the seam's only real test. If `ask.py` needs one edit to run on
Postgres, the Protocol was decoration. The measurable claim is that the pipeline
file is untouched by this session.

The second reason is the one the dict cannot fix: **the in-memory idempotency
check is not safe across processes.** Two `uvicorn` workers, or two replicas
behind a load balancer, each hold their own `_by_client` dict, so the same
`client_message_id` posted twice lands on two workers and creates two turns and
two provider calls. D-02 is registered `done` on the strength of a guarantee that
holds only at one worker. The unique constraint is what makes it true.

Two items on the gate list are not S7's, and one of them changes the running

### T-16 must pass, and it currently `xfail`s

`XFAIL … R-02: no sufficiency gate in ask.py … Owed by S6b`. T-05 and T-10 pass.
S6 wrote T-16 red on purpose and pinned it with `xfail(strict=True)`; the gate
asks for it green. **That is S6b's work, not S7's**, and no amount of storage
closes it.

### S7 makes the T-18 leak durable, which is the stronger argument

This is the load-bearing scheduling point, and it is new information rather than
a restatement of S6.

S6 measured that a PII-bearing corpus chunk reaches the caller twice — in
`answer` and in `citations[0].snippet` — because `redact()` never runs in the
pipeline and `citation_from_evidence()` copies `evidence.text` verbatim. Today
that leak is **transient**: it lives in one HTTP response.

S7 writes both to disk. `messages.answer_text` and `citations.snippet` are
exactly the two leaking values, and after this session they are persisted,
retained, included in every backup, and readable by anyone with a psql prompt —
including, once S8 lands, replayed into the browser on every history load. A
transient leak becomes a durable one, and the remedy stops being "fix the
scrubber" and becomes "fix the scrubber **and** clean the table."

**Therefore the order is `S7a → S6b → S7b/c`, and that is the plan rather than a
contingency.** It falls out of what each step does: S7a creates tables and
persists nothing, so it is safe to land first and it unblocks nothing dangerous.
S6b is what stops `messages.answer_text` and `citations.snippet` from
accumulating unscrubbed PII the moment S7b wires the repository in. Sequencing it
between the two costs nothing and removes the need for a stopgap that would not
work anyway — `redact()` cannot remove names (S6 finding 3), so a scrub-on-insert
patch would persist four of gs-010's five forbidden names while looking like a
fix.

The gate wanting T-16 green is a second, weaker reason to run S6b here. The first
one would hold even if no gate mentioned it.

### The "fewer than 25 tests" line is retired, not failed

Measured: 47 test functions, 55 collected, 1 deselected.

That line was a runbook proxy for *do not pad the suite*, not a requirement from
the brief, which says nothing about test count. The underlying property is now
enforced directly and more strictly than a count could: every test function's
docstring carries a `T-nn / R-nn` pair, and `scripts/traceability.py` fails CI on
a requirement with no test. A number cannot distinguish a padded suite from a
thorough one; the mapping can.

So the proxy is retired in favour of the direct measure, the same way the
`plainto_tsquery` assumption and the caption regex were replaced by counts taken
against the real corpus. Collapsing T-19's eight functions into parametrised
cases would produce nothing an evaluator can see, risk breaking green tests, and
spend a commit doing it. `DECISIONS.md` gets one line saying the gate was a proxy
and naming what replaced it.

**No consolidation commit.** S7 is three commits, not four.

## Decisions taken before writing this

### 1. Alembic owns the whole schema, including `chunks`

`001_chunks.sql` is applied today by `apply_migrations()` on every
`create_pool()`. Leaving it there and adding Alembic for the conversation tables
puts two schema tools on one database, which is how a staging box ends up with a
column production does not have.

So the initial Alembic revision **subsumes `001_chunks.sql`**, `db.py` stops
executing SQL on pool creation, and the file is deleted rather than left as a
decoy. The revision is written by hand rather than autogenerated for the chunks
half, because `tsv` is a generated column and `embedding` is a `vector(1536)` —
neither round-trips cleanly through autogenerate, and a migration that silently
drops the `GENERATED ALWAYS AS` clause takes the lexical arm of retrieval with it.

### 2. SQLAlchemy for the conversation store; retrieval keeps its hand-written SQL

`hybrid.py` is one gated SQL statement carrying an OR'd `tsquery`,
`ts_rank_cd(..., 32)`, RRF at `k=15` and a `doc_role` multiplier. Every one of
those numbers was measured against the real index in S3 and is quoted in
`DECISIONS.md`. An ORM adds nothing to it and obscures the thing a reviewer needs
to read.

So: **SQLAlchemy Core** (not the ORM — no declarative models, no relationships,
no lazy loading) for `models.py` and `sql.py`; `hybrid.py` untouched. Core gives
Alembic a schema to diff against and gives `sql.py` parameter binding, which is
all that is wanted.

**Two pools, named as a cost.** `hybrid.py` keeps its `asyncpg` pool; `sql.py`
gets a SQLAlchemy async engine. Both point at one Postgres. The alternative —
running the retrieval SQL through `session.execute(text(...))` — needs
`register_vector` re-plumbed through SQLAlchemy's connection lifecycle and risks
a measured, working retrieval path for no functional gain. The cost is roughly
double the idle connections, capped by `pool_size` on the engine and already
bounded on the asyncpg side. Consolidating to one engine is a follow-up, not a
prerequisite.

### 3. The status enum is generated from the Python `Literal`, not retyped

`TurnStatus` in `app/domain/models.py` already spells the five values. Writing
them again in `models.py` creates two sources of truth that drift on the day
someone adds a sixth.

```python
from typing import get_args
from app.domain.models import TurnStatus

message_status = Enum(*get_args(TurnStatus), name="message_status")
```

A native Postgres enum, per the instruction. The usual objection —
`ALTER TYPE … ADD VALUE` cannot run inside a transaction on older servers — is
real and does not apply: S1 closed this vocabulary deliberately, `failed` was
added on day one precisely so the history surface would not need a migration, and
a sixth value would be a design change rather than a schema tweak.

A test asserts the database's enum labels equal `get_args(TurnStatus)`, so the
generation cannot silently stop matching.

### 4. Ordering is an identity column, not a timestamp

The gate is "replays … **in order**". `created_at timestamptz` ties: two turns
inserted in the same millisecond order nondeterministically, and the test passes
until the day it does not. `seq bigint GENERATED BY DEFAULT AS IDENTITY` with
`ORDER BY seq` is total and monotonic. `created_at` stays, because it is what a
human reads, but nothing orders by it.

### 5. `begin_turn` keeps its three branches, now decided by the database

S1 specified the shape and S7 executes it unchanged:

```sql
INSERT INTO messages (...) VALUES (...)
ON CONFLICT (conversation_id, client_message_id) DO NOTHING
RETURNING *;
```

No row back means a conflict; read the existing row and branch on its status —
`pending` → `in_flight`, anything else → `replay`. Same three branches `ask.py`
already handles, now race-safe across workers rather than within one.

The conversation row is created the same way (`ON CONFLICT DO NOTHING` on
`conversations`) in the same transaction, so a first message to an unknown
conversation id works exactly as it does today. **No `POST /conversations`.**
The API is URL-addressable by design and a create endpoint would be a speculative
surface the rule forbids and the web client does not want.

### 6. `citations` denormalises `document_code` and `version` on purpose

The gate wants "which answers cited NI-014 v1.0?" as one SQL statement. A
`chunk_id` foreign key alone technically satisfies "one statement" via a join —
and gives the wrong answer. Documents get superseded; `chunks` carries the
version as it is **now**. A citation must record what was cited **then**, or the
day NI-014 v3.0 lands, every historical answer retroactively claims to have cited
it.

So `citations` carries `evidence_id`, `document_code`, `document_title`,
`section`, `version`, `effective_date` and `snippet` as a point-in-time record.

**`chunk_id` is a plain `text` column with no foreign key**, and that is the same
argument carried to its conclusion. A citation is a historical record
*deliberately decoupled* from the current index — which is the entire reason
`document_code` and `version` are denormalised one paragraph up. An FK would
re-couple the two and buy only "provenance while the chunk still exists," which
is the weakest half of what the column is for.

The operational cost is concrete. Ingest is upsert-based today
(`INSERT … ON CONFLICT DO UPDATE`, `executemany` in one transaction), so an FK
would not error on a routine re-ingest of the same chunk ids. It bites on the
next thing anyone would reasonably do: a **re-chunk**. Change the parser, the
caption regex or the chunk boundaries and the ids move, so the clean way to
re-index is `TRUNCATE chunks` — and Postgres refuses to truncate a table
referenced by a foreign key. The escapes are `TRUNCATE … CASCADE`, which deletes
the citation history, or rewriting ingest to `DELETE`. Neither is a trade worth
making for a constraint whose own semantics we do not want.

Dropping it also lets a claims-sourced citation (`evidence_id` is a query call
string, with no chunk row anywhere) sit in the same table without a special case.

`DECISIONS.md` records it in one line — *no FK to chunks: citations are
point-in-time, and ingest must stay free to truncate and re-chunk* — so it reads
as a decision rather than a missing constraint.

```sql
SELECT m.id, m.question, m.answer_text
FROM citations c JOIN messages m ON m.id = c.message_id
WHERE c.document_code = 'NI-014' AND c.version = '1.0'
ORDER BY m.seq;
```

### 7. History and LLM context are two different reads of one table

Easy to conflate, and conflating them is a bug in both directions.

- `recent_messages()` feeds the model. It **skips** `failed` and `pending` turns
  — a failure is not a conversational turn, and replaying it invites the model to
  apologise for an error the analyst never saw. This is existing behaviour in
  `memory.py` and `sql.py` must preserve it.
- `GET /conversations/{id}/messages` renders for a human. It **includes** all
  five statuses, `failed` with its `error_code`, `pending` with a null answer,
  because S1 put `failed` in the enum for exactly this surface.

Two methods, two queries, one table. The contract test asserts the difference
rather than leaving it to be rediscovered.

### 8. `prompt_version` is a hash, and it is meant to invalidate things

`sha256(system_prompt + json.dumps(DRAFT_SCHEMA, sort_keys=True))`, first 12 hex
characters, computed once at import. Stored per message.

It answers "which answers were produced by the prompt we are about to change?"
in one query, and it is the key `30-tests.mdc` already assumes for Tier 1
cassettes: "A prompt change invalidates cassettes — that failure is correct
behaviour." A column that makes a stale cassette *visible* is worth more than one
that records a version number nobody bumps.

### 9. `cached_tokens`, and the wire name does not follow it

The instruction names the column `cached_tokens`; the domain model and the
envelope say `cached_prompt_tokens`. The column takes the shorter name — inside a
`messages` row every token count is already scoped to one message — and `sql.py`
maps it explicitly.

**`UsageOut.cached_prompt_tokens` does not change.** T-02 asserts the usage keys
exactly, the web client reads them, and renaming a wire field to match a column
name is the tail wagging the dog. The mapping lives in one function and is
covered by the contract test.

## Schema

```sql
CREATE TYPE message_status AS ENUM
  ('pending', 'answered', 'refused', 'needs_clarification', 'failed');

CREATE TABLE conversations (
  id          text PRIMARY KEY,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE messages (
  id                 text PRIMARY KEY,
  conversation_id    text NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  client_message_id  text NOT NULL,
  seq                bigint GENERATED BY DEFAULT AS IDENTITY,
  question           text NOT NULL,
  status             message_status NOT NULL DEFAULT 'pending',
  answer_text        text,
  error_code         text,
  reason             text,
  model              text NOT NULL DEFAULT '',
  prompt_version     text NOT NULL DEFAULT '',
  latency_ms         integer NOT NULL DEFAULT 0,
  cost_usd           numeric(10, 6) NOT NULL DEFAULT 0,
  prompt_tokens      integer NOT NULL DEFAULT 0,
  completion_tokens  integer NOT NULL DEFAULT 0,
  cached_tokens      integer NOT NULL DEFAULT 0,
  degraded           boolean NOT NULL DEFAULT false,
  created_at         timestamptz NOT NULL DEFAULT now(),
  completed_at       timestamptz,
  CONSTRAINT messages_client_idem UNIQUE (conversation_id, client_message_id)
);
CREATE INDEX messages_conversation_seq ON messages (conversation_id, seq);

CREATE TABLE documents (
  id             text PRIMARY KEY,          -- document_code, e.g. CG-AUTO-2024
  title          text NOT NULL,
  version        text NOT NULL,
  effective_date date NOT NULL,
  product        text NOT NULL,
  doc_role       text NOT NULL,
  superseded     boolean NOT NULL DEFAULT false,
  source_path    text,
  ingested_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE citations (
  id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  message_id     text NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  ordinal        integer NOT NULL,
  evidence_id    text NOT NULL,
  chunk_id       text,                      -- deliberately NOT a foreign key; see decision 6
  document_code  text NOT NULL,
  document_title text NOT NULL,
  section        text NOT NULL,
  version        text NOT NULL,
  effective_date date NOT NULL,
  snippet        text NOT NULL,
  CONSTRAINT citations_message_ordinal UNIQUE (message_id, ordinal)
);
CREATE INDEX citations_document ON citations (document_code, version);
```

`chunks` keeps its S2/S3 columns and gains
`document_id text REFERENCES documents(id)`. `documents` is populated by ingest
and read by the provenance footer (D-05).

**The duplication is a kept tradeoff, not deferred cleanup.** The tempting note
here is "remove the denormalised columns from `chunks` in S8" — and that is how
S8 slips, because S8 owes a mandatory requirement and a schema refactor riding
along is unbudgeted risk against a graded deliverable. The honest version:
`hybrid.py` selects those columns by name inside a query whose ranking constants
were measured against the real index, and **rewriting a measured retrieval query
to save a join across thirteen documents is not worth the risk at this scale.**
That goes in `DECISIONS.md` in those words, with the scale named — a named
tradeoff someone kept on purpose reads better, and is more honest, than a
deferred fix that quietly never happened.

`numeric(10, 6)` for `cost_usd`, not `double precision`. Money summed over
thousands of rows in float drifts, and the one question this column exists to
answer is "what did we spend."

**One new failure mode S7 introduces**, named because the resilience gate is
about the ladder holding: with `STORAGE=sql`, the degraded path now depends on
the database. Provider down + retrieval up still returns excerpts — but only if
`complete_turn` can write. A database outage is therefore a 503 on every rung.

**That is a domain decision, not a technical convenience.** The reason is not
that idempotency is hard to honour without a database; it is that **an answer
which cannot be recorded should not be given.** The citation record is this
product's compliance artifact — the thing that lets someone reconstruct, months
later, which normative version an analyst was shown and acted on. Serving a
cited answer while unable to record what was cited produces exactly the state the
whole design exists to prevent. It is the same reasoning that made `citations` a
table rather than a JSON blob on the message.

It is still a *new* single point of failure the ladder in `S5.md` does not draw,
which is why `/healthz` reporting `database.reachable` makes it diagnosable
rather than mysterious.

**Pool sizes are set explicitly, not left at defaults.** Two pools per process
against one Postgres is unremarkable at one worker and a real problem at four:
SQLAlchemy defaults to `pool_size=5, max_overflow=10` and asyncpg to
`min_size=10, max_size=10`, so four workers can reach ~100 connections against a
default `max_connections=100`. B-10's twenty concurrent questions is precisely
when that would be discovered. Both get small explicit numbers
(`pool_size=5, max_overflow=5` on the engine; `min_size=2, max_size=10` on the
asyncpg pool), and `docker-compose.yml` sets `max_connections` above the worst
case rather than relying on the default.

## Out of scope for S7 — stated so it is not mistaken for an omission

The five pieces of grounding work S6 assigned to **S6b** — sufficiency gate,
ambiguity gate, PII refusal, `redact()` in the pipeline, the snippet and log
egress paths. They run *between* S7a and S7b rather than after S7, but they are
S6b's plan, not this one's. Consolidating retrieval onto the SQLAlchemy engine.
`GET /conversations` as a list endpoint — no requirement asks for it. The React
history view (**S8**, mandatory, and the thing S7 must not eat into). Streaming
(D-01). Cassette-keyed Tier 1 replay, which `prompt_version` enables but does not
implement (S9).

**Not out of scope — decided and kept:** the `documents` / `chunks` column
duplication. It is not on a removal schedule, because a schema refactor riding
along on a session that owes a graded deliverable is how that session slips. See
the schema section.

**`ask.py` gets exactly one edit this session**: `PROMPT_VERSION` passed to
`complete_turn`. If a second becomes necessary, stop and say so in the commit
message — it means `ConversationRepository` was the wrong shape, and that is a
finding worth more than a quiet fix.
